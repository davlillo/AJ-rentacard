# Rental accounts stage and rental detail document
Objective: Add a Cuentas stage to the rental pipeline with honest money separation, and a client-side PNG/PDF detail document of a reservation.
Branch: feature/pruebas; local only, no commits/push, no database writes or migrations. Checks: isolated tests, synthetic browser fixtures, TypeScript and production build. Engram mirror pending unresolved project identity.

## Specs
- S1: “igual en alquileres deberia haber como generar un pdf o un imagen png con los detalles de la reserva o alquiler” — Offer a downloadable PNG and PDF with the rental details: folio, customer, vehicle, agreed dates, duration in days and the agreed amount. Client-side generation only, no stored artifact, no new persisted contract.
- S2: “acordar detalles como los dias, el vehiculo a quien se le alquila y el costo acordado” — Include the agreed amount with its exact meaning. Three distinct values exist (contracted total, issued documents, accrued forecast); the document must label each one and never present a forecast as an agreed price or a receivable.
- S3: “ese costo acordado seria como el cuneta por cobrar de ese behiculo” — Treat the agreed amount as the customer agreement, not as an issued receivable. A receivable exists only after the canonical period command issues a billing document. No schema change is authorized: the period command and the linked receipt commands already exist.
- S4: “el flujo ese el pipeline antes de finalizardo deberia haber la seccion de cuentas de ese alquiler lo acordado, agregar mas y cobrar saldar cuneta” — Insert a Cuentas stage between Devolución and Finalizado, derived from persisted money evidence: agreed forecast, issued amount, applied money, pending balance and available advance. Provide three actions: emit the amount for a period (canonical command, explicit manual amount, contiguous non-overlapping dates), register a collection, and apply an available advance.
- S5: “agregar mas” — Implemented as issuing additional canonical periods over the contractual range, which the server already allows, plus explicitly confirming the full agreed amount as one period. Free-form extras beyond the contractual dates are not available without a new scoped command and are reported as a limitation, not invented.
- S6: Money semantics must stay truthful: receipt is not application; agreed is not issued; advance already received is not new income; grouped document balances belong to the group; closing a folio does not extinguish a receivable and must not be silently blocked because a balance remains, consistent with the workshop delivery contract that already preserves debt.
- S7: Reuse the existing document projection discipline: a client-safe whitelist with no internal cost, margin or operator fields; reuse the existing pdf-lib/fontkit pipeline, its font asset and download helpers; render PNG through a dedicated renderer because the quote image renderer requires quote content and hardcodes quote labels.
- S8: Verify the font subset actually supports the Spanish glyphs used (accents, ñ, ¿, em dash, middle dot) because the PDF pipeline throws on unsupported glyphs; fall back to a supported font file or safe wording rather than crashing the download.
- S9: Preserve existing rental behavior, permissions, stages, legacy section aliases, guards, versions, idempotency and the shared collection dialog used by rentals. Money visibility keeps the current permission and access-flag gate. No schema change, no new accounting policy, no invented receipt, no double counting.
