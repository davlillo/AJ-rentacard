# Rental module closure: identity documents, agreement card and a simpler folio
Objective: Close the rentals module the way the operator actually works — a readable identity-document viewer, a proper rental agreement card whose client document exists before the handover, and a folio with fewer, clearer sections.
Branch: feature/pruebas; local only, no commits/push, no database writes or migrations. Checks: isolated tests, synthetic browser fixtures, TypeScript and production build. Engram mirror pending unresolved project identity.

## Specs
- S1: “en cliente al darle ver foto de dui se abre hasta abajo o sea que salga en un modal así esa parte de documentos de identidad la ui está horrible tiene el formato antiguo” — The customer identity document viewer opens the DUI or licence image in an accessible modal with title, close, focus return and Escape, not appended under the list. Restyle that section to the current UX standard: clear card per document kind, honest empty state, the existing privacy statement, and no change to who may read those private files.
- S2: “el alquiler el card de acuerdo de alquiler en la fase de igual en resumen deberían ser los acuerdos como tal así detallada” — The Resumen agreement card presents the rental agreement as such and in detail: client, vehicle, delivery and return dates, duration, daily rate and agreed total, with the current status.
- S3: “el detalle de alquiler debe ser para el cliente o sea se debe generar al hora de hacer la reserva o el alquiler no después o sea se le envía antes de darle el carro” — The client detail document (PDF and PNG) is available at agreement time, not only later: the creation wizard offers it right after the reservation is confirmed, and the agreement card in the folio offers it before the handover step, with plain wording that it is what the client receives. Generating it never issues money, never approves anything and never stores a contractual artifact.
- S4: “Cargos y abonos … no sé qué significa … Documentar otro período de alquiler … esto debería estar en otra parte porque en serio no funciona así” — The folio stops showing the period-documenting form in a section called Cargos y abonos. Documenting a period stays available only as the extension action of an active rental, where it belongs, and the legacy section URLs keep working.
- S5: “solo es alquilar carros y cobrar” — The money block leads with three facts an operator actually needs, each with a one-line explanation: what was agreed, how much has been collected, and what is still pending. The technical detail (issued documents, applied amounts, document balance, advances) moves into a collapsed detail so it stays available without dominating. No number is invented and no total mixes different kinds of money.
- S6: The pending amount must be explainable: an agreed amount is a receivable only once a document is issued, so the interface says in plain words what is agreed, what is already invoiced and what still has to be invoiced, instead of the current bare “Acordado sin emitir — no es saldo pendiente”.
- S7: “quitemos lo de limpieza” — The Limpieza tab is removed from the folio navigation; the cleaning review remains reachable and mandatory from the return flow, with its existing guards and evidence requirements untouched. Legacy section URLs for Limpieza keep resolving.
- S8: Preserve every capability, permission, guard, version, idempotency key and legacy link. Money semantics stay canonical: agreed is not issued, a receipt is not applied, an advance is not new cash, the server owns the balance, and grouped shares stay with the group. No schema change, no new accounting rule, no stored artifact.
